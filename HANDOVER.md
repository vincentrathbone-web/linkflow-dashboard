- **Hold-to-stop race fixed: stopping the timer could immediately restart a new session (2026-08-19, desktop 0.1.22).** Reported by the user right after confirming 0.1.21's popup itself worked correctly — stopping via the floating widget's hold gesture would stop/log the session (popup opened fine) but then *immediately* start a brand-new session too. Root cause was in `useHoldToStop.ts`, not the new popup: when the 1.5s hold completes, `tick()` fires `onHoldComplete()` (the stop) — but the user is typically still physically holding the pointer down at that instant. The main window broadcasts the new "idle" phase back to the floating widget very quickly (a single event round-trip, much faster than opening a whole new window), and if that lands *before* the user actually lifts their finger, the widget's local `phase` flips to `'idle'` mid-gesture, so `holdEnabled` (`phase !== 'idle'`) becomes `false` while the same physical press is still in progress. `onPointerUp`'s closure gets rebuilt with that stale-but-now-false `holdEnabled`, so when the real release finally fires, it hits the `else if (!holdEnabled)` branch — meant for "a plain click while already idle" — and calls `onShortPress()`, starting a new session right after the stop. This bug likely predates the 0.1.21 popup (the old in-window modal could have masked it, or made it less noticeable); the visible always-on-top popup just made it obvious.
  - **Fix:** a new `completedRef` in `useHoldToStop.ts` tracks whether `onHoldComplete` already fired for the press currently in progress; `onPointerUp` checks it first and, if set, treats the release as trailing cleanup and returns immediately — regardless of what `holdEnabled` has changed to underneath it in the meantime. Reset on the next `onPointerDown`. Shared by both the floating widget and the in-app Timesheet panel button (same hook), so this covers both surfaces. The tray icon's own hold-to-stop is unaffected — it's separate Rust logic (`TrayPressState` in `lib.rs`) that decides toggle-vs-stop from elapsed time at the moment of release, with no phase/holdEnabled dependency, so it was never susceptible to this race.
  - **Confirmed working by the user's own hands-on install/test** of the signed 0.1.22 build — hold-to-stop via the floating widget no longer restarts a session. Verified via `npm run lint`, `cargo check`, both Vite build modes, and a signed `tauri build --target x86_64-pc-windows-msvc`. Published as GitHub Release [`v0.1.22`](https://github.com/vincentrathbone-web/linkflow-dashboard/releases/tag/v0.1.22); update proxy confirmed live (`current_version=0.1.21` → 200 with a valid signed 0.1.22 manifest, `current_version=0.1.22` → 204). No plugin deploy needed — frontend-only, plugin stays at 0.4.33.

- **Play/Pause/Stop timer redesign (2026-08-19): implemented across the floating widget, the main Timesheet panel, and the tray icon; published as desktop 0.1.18 and deployed as plugin 0.4.32; confirmed working by the user's own hands-on testing, including the tray fixes above.** Preceded by an approved interactive design canvas (a Claude Design canvas artifact showing the three colors, the press-in emboss material, and the hold-to-stop sweep — see the conversation, not persisted to this repo). Replaces the old binary running/stopped clock with three states:
  - **Data model**: `TimesheetState` gained two fields, `sessionStartedAt: string | null` (the original clock-in moment of the in-progress session, survives pause/resume, becomes the logged session's `start` on Stop) and `pausedElapsedMs: number` (time banked from earlier run segments before the most recent pause). `currentSessionStart` now means "this exact run segment is ticking," not "a session is in progress" — a session can be in-progress (`sessionStartedAt` set) while `currentSessionStart` is null (paused). Phase is always derived from these two (`getTimerPhase()` in `src/lib/time.ts`), never stored as a separate enum, so it can't drift out of sync. `getLiveElapsedMs()` sums banked + live-segment time; both new fields default via `DEFAULT_TIMESHEET` and are coalesced against `undefined` at the read sites (`pausedElapsedMs || 0`), since a pre-existing `localStorage` cache or an unmigrated server response won't have them yet.
  - **Interaction**: a short press starts (idle), resumes (paused), or pauses (running) — decided in one atomic `setTimesheet` functional update, `handleTimerShortPress` in `App.tsx`. Holding for 1.5s (`HOLD_TO_STOP_MS`) instead finalizes and logs the session via `handleTimerHoldComplete` — allowed from *either* running or paused, not just running, so a paused session isn't a dead end. Both the floating widget and the main panel share one hook, `src/lib/useHoldToStop.ts`, that owns the press/hold state machine (pointer down/up/leave, a `requestAnimationFrame` progress loop, cancel-on-early-release, a ~450ms hold-at-100%-then-reset beat so the completed "stopped" visual actually gets to paint before the state resets) — written once rather than duplicated between the two surfaces.
  - **Colors and material**: green (`#22c55e`, idle/paused), blue (`#3b82f6`, running), near-black (`#17181c`, shown only while/just after a completed hold) — literal hex values, not the app's themed `bg-brand`/`bg-danger` tokens, matching the approved design exactly. The floating widget's button is a flatter, rounder-edged puck than its first pass (no more glossy radial-gradient "skittle" look) with a soft-rubber press: releasing swaps between two box-shadow recipes (raised: light inset top-bevel + dark inset bottom-bevel; pressed: the reverse plus a stronger top-inset shadow) so it reads as the surface *bending inward* under pressure rather than just sinking or scaling down. The main panel's Start/Stop pill keeps the app's existing flat button chrome (no emboss) but gained the same three colors, bigger icon, and the same hold-to-stop sweep — per explicit scoping, only the *logic* needed to match, not the floating widget's skeuomorphic material.
  - **The 1.5s hold sweep**: a dark (`#17181c`) mask-image reveal, `linear-gradient(90deg, ...)` clipped to the current hold progress, layered over the button so it visually "fills in" left-to-right and reads as the button charging toward Stop.

  - **PHP**: `sanitize_workspace()`'s timesheet block gained `sessionStartedAt`/`pausedElapsedMs`, following the exact same "missing key falls back to the previously-stored value, not a hardcoded default" pattern established for the 0.4.30 data-loss fix — an old desktop client that predates pausing would otherwise silently wipe a paused-but-not-yet-logged session's banked time on its very next unrelated save.

- **Floating timer widget + tray icon timer (2026-08-19): implemented, iterated through five hands-on bug rounds, and confirmed fully working by the user as of desktop 0.1.16.** Two new independent, opt-in ways to keep the Timesheet clock visible outside the main window (both desktop-only, both per-device `localStorage` preferences, gated behind `isDesktopApp()` — neither shows on the hosted web page or syncs to the cloud):
  - **Floating widget**: a small always-on-top, chromeless, transparent window (`#timer-widget` hash route, `TimerWidget.tsx`) showing just a circular Play/Stop button (blue+white-play when stopped, red+white-stop when running, using the app's existing `bg-brand`/`bg-danger`/`text-inverse` tokens) with the live elapsed time below it (deliberately literal white text + a fixed drop-shadow, not a theme token, since it floats over arbitrary desktop wallpaper rather than the app's own themed surface). Draggable via a small grip badge that only appears on hover (`data-tauri-drag-region`), separate from the button's own hit area so an accidental drag-attempt near the button's edge can never register as a stop-click; opens in the primary monitor's bottom-right corner by default (position isn't remembered across restarts — would need `tauri-plugin-window-state`, not added). `App.tsx`'s `openTimerWidget()`/`closeTimerWidget()` mirror the existing `openDiagnosticsWindow()` second-window pattern.
  - **Tray icon**: built once at startup in `src-tauri/src/lib.rs` (new `tray-icon` Cargo feature on the `tauri` dependency), hidden by default, shown/hidden via a new `set_tray_visible` command as the Settings toggle changes. Its icon is drawn programmatically in Rust as raw RGBA (`tray_icon_image()` — a hand-rasterized circle plus a play triangle or stop square, no PNG asset), swapped live between blue-play and red-stop via `set_tray_running`. Tooltip is pushed live from JS (`set_tray_tooltip`, once a second while running) since Rust has no view into the JS-owned timesheet state on its own. Left-click toggles start/stop directly (`.show_menu_on_left_click(false)` — Windows' tray default is to also pop the menu on a plain left-click, which fought with the toggle-click until explicitly disabled); right-click opens a menu (Start/Stop Clock, Show LinkFlow, Quit).
  - **State flow**: `App.tsx` is the single source of truth (exactly as it already is for the main window's own Timesheet panel). It emits a Tauri event (`linkflow://timesheet-state`, `{ currentSessionStart }`) whenever the clock starts/stops and whenever the widget window signals it just opened (`linkflow://timer-widget-ready`); the widget then computes its own live elapsed time locally via its own 1-second tick, the same computation `TimesheetPanel.tsx` already does — no per-second IPC. Both the widget's button and the tray's menu item toggle the real clock via one shared `linkflow://timer-toggle` event, listened for once in `App.tsx` (using a ref to read the latest `currentSessionStart` without needing to resubscribe on every Start/Stop). This is the first use of Tauri's JS event `emit`/`listen` API anywhere in this codebase.
  - New capability file `src-tauri/capabilities/timer-widget.json` scoped to the `timer-widget` window: `core:default`, `core:event:default`, and `core:window:allow-start-dragging` — the last one is not part of any default permission bundle and its absence fails *silently* (no console error, no denied-permission log visible in production; the drag JS just never fires its `invoke`), so it's easy to ship a build that looks complete and still doesn't drag.

  - **Five real bugs were found and fixed only by the user running each build by hand** — type-checking and a successful build caught none of them:
    1. The whole widget window was originally one big drag region, so a click near the Stop button's edge could register as a drag-start instead of a click, accidentally stopping the clock. Fixed by moving dragging to a small separate hover-revealed grip, away from the button's hit area.
    2. The tray showed the static app icon regardless of state. Fixed by drawing the icon procedurally in Rust instead of loading a fixed asset (see `tray_icon_image()` above).
    3. Tray left-click both toggled the clock *and* opened the context menu (Windows' tray default). Fixed with `.show_menu_on_left_click(false)`.
    4. The grip's negative-offset positioning (`top: -10px, right: -10px` relative to a box sized exactly to the button) got clipped by the ancestor/window bounds. Fixed by sizing the parent positioning box to fully contain both the button and the grip using only non-negative offsets, rather than letting a child render outside its parent's box via negative margins/offsets.
    5. **The drag still didn't work even after the clipping was fixed and the `core:window:allow-start-dragging` permission was added.** Root cause, found by reading Tauri's own injected drag script (`tauri-2.11.5/src/window/scripts/drag.js`): a *bare* `data-tauri-drag-region` attribute only starts a drag when the raw click **target** (`event.composedPath()[0]`) is that exact element — but the grip's visible content was an inner `<svg>`/`<circle>` icon, so every click's real target was the icon, not the div carrying the attribute, and the check silently never matched. Changing the attribute to `data-tauri-drag-region="deep"` (documented as "any descendant click triggers the drag") fixed it immediately. **Lesson for next time a `data-tauri-drag-region` element wraps any child content** (an icon, text, anything): use `"deep"`, not the bare/`"true"` form, unless the element is truly a leaf with nothing else inside it — the bare form's exact-target-match requirement is not obvious from the attribute alone and fails with no error at all.

## Architecture

The React code is shared between the optional WordPress page and the Windows client. Vite selects its output by build mode:

- `npm run build` writes plugin assets to `wordpress-plugin/linkflow-dashboard/build/`.
- `npm run build:desktop` writes native-client assets to `linkflow-dashboard/dist/`.
- `tauri build` embeds the desktop assets and creates Windows installers.

WordPress owns identity, device tokens, workspace persistence, sanitization, revision history, and optimistic version checks. The desktop client owns native presentation and Windows Credential Manager integration.

## Authentication flow

1. The user enters the WordPress URL, username/email, and password in the desktop client.
2. The client sends them once over HTTPS to `POST /desktop/session`.
3. The plugin authenticates with WordPress, generates a 256-bit device token, stores its SHA-256 hash, and returns the raw token once.
4. Tauri stores the raw token in Windows Credential Manager under service `za.co.controll.linkflow`.
5. Subsequent API requests use `X-LinkFlow-Token`.

The WordPress password is never retained. Tokens are per-device and revocable.

## Workspace write flow

1. React state and localStorage update immediately.
2. An 800 ms debounce consolidates rapid UI changes.
3. The client sends `POST /workspace` with the complete workspace and `X-LinkFlow-Version`.
4. WordPress authenticates the device token, validates and sanitizes the document, writes the user row, increments the version, and records a revision.
5. The client stores the returned version. The temporary diagnostic console records both successful and failed steps with a shared request ID.

The application loads cloud state at startup only; it does not poll or receive server-pushed changes, so an already-open client cannot see a server edit automatically. This is intentional, not a pending gap: the server exists as the recovery/device-switch path (see the 2026-08-01 architectural decision below), and the desktop `POST` on every change is the real synchronization contract. The diagnostic console states the startup-only pull explicitly so this isn't mistaken for continuous sync.

## Temporary synchronization diagnostics

Desktop 0.1.2 and plugin 0.4.5 added the visible diagnostic console shown during restoration, sign-in, initial loading, and normal app use; it is still present in 0.4.9. Up to 500 events persist in local storage and can be copied or cleared. Each cloud request carries `X-LinkFlow-Request-ID`, allowing the client log to match the server response. The server reports authentication state, WordPress user ID, plugin version, current/expected/new workspace versions, payload size/counts, database write mode, affected rows, revision result, and UTC timestamp. GET responses are explicitly no-cache and the desktop adds a timestamp query value.

Passwords, raw device tokens, authorization headers, nonces, and secret-like fields are redacted. This panel is intentionally temporary and should be removed or placed behind an explicit support mode after synchronization is verified.

## Architectural decisions

### 2026-08-18

- Added a To-Do List and Timesheet side panel pair, requested as "a to-do list/tracker and timesheet (start/stop clock)". A layout mockup was shown first as a Claude Design canvas artifact (two directions — a compact list vs. a grouped/tracker-style layout); the user picked the grouped direction ("Option B") and confirmed two scoping decisions before any code was written: (1) cloud-synced, not a local-only per-device preference like the cat toggle or Daily Inspiration mode — the data needs to follow the user between the desktop app and the hosted page; (2) single-user only — the mockup's assignee-avatar idea (JM/KP/TR chips) was dropped entirely, no cross-account assignment/sharing.
- Investigated the existing sync architecture before designing the data model and found the entire `workspace` document is stored as one JSON blob in a single `longtext` column (`wp_linkflow_workspaces.workspace`), not per-field DB columns. This meant the feature could be added with **zero schema changes** — no new table, no `LINKFLOW_DASHBOARD_DB_VERSION` bump — just two new optional keys (`todos: TodoItem[]`, `timesheet: TimesheetState`) on `WorkspaceDocument` (`linkflow-dashboard/src/lib/linkflowApi.ts`) and a matching extension to `sanitize_workspace()`'s whitelist. Establishes the pattern for any future per-user structured-data feature on this app: check whether it can ride the existing single-document sync contract before reaching for a new table/endpoint.
- To-Do "Today"/"This Week" grouping is derived client-side from `dueDate` on every render, not stored as a separate field — a stored `group` enum would go stale as dates pass at midnight with no code path to correct it. Same reasoning applies to the timesheet's live elapsed-time display: it's computed from `currentSessionStart` (a plain persisted ISO timestamp) against a local `Date.now()` tick every second, entirely inside `TimesheetPanel.tsx` — that per-second tick never touches the synced `timesheet` state or the debounced-save effect's dependency array, so only the two discrete Start/Stop events trigger a cloud write, not every second of an open session.
- New icons (checklist, clock, flag, play/stop) were hand-drawn as inline SVG rather than using the app's existing `material-symbols-outlined` ligature-icon font, specifically because this same file already documents a real production bug (0.4.21, see below) where that exact font rendered as literal text under WordPress/Elementor isolation. Standard chrome already proven safe elsewhere (modal close buttons, the delete/add icons) still uses `material-symbols-outlined` for consistency — only the genuinely new icon shapes got the SVG treatment.
- Per explicit correction mid-implementation: every color in the new components is one of the app's existing semantic Tailwind tokens (`bg-brand`, `text-danger`, `text-star`, `border-border-main`, `text-text-inverse`, etc.), never a literal hex value — this matches a rule already stated in the root `README.md`'s "Theming" section ("Hardcoded `slate-*`/`font-sans` classes are not permitted outside `index.css` itself") that the first draft of `TodoPanel.tsx` briefly violated (hardcoded priority-flag hex colors) before being corrected.
- **Not yet done, deliberately left for a separate step:** no plugin version bump, no desktop version bump, no deploy to `controll.co.za`, and no live verification. Implementation was checked locally only (`npm run lint`, both Vite build modes, PHP lint, `package.ps1 -NoBump`) — see Status above and "Next checks" below for exactly what a live check still needs to cover.
- **Same day, follow-up request:** made the To-Do/Timesheet panels draggable between the left/right columns (or reorderable within one) and resizable in height only, snapped to a grid so they can never overlap each other or the center Dashboard block, "using the same effect as the link setup kanban board." Read `SortBoard.tsx` (`src/components/onboarding/SortBoard.tsx`) in full first: it's a fully hand-rolled Pointer Events + Web Animations API implementation (no `@dnd-kit`/`react-dnd`/`react-grid-layout` anywhere in this repo) built on four techniques — a dual-track ref+state session (ref mutated synchronously in pointer handlers, state only updated when the drop target changes, not per pixel), one `getBoundingClientRect()` layout snapshot taken at pointerdown and never re-measured during move, velocity-derived tilt (EMA-smoothed pointer velocity, clamped ±5deg, with a 70ms settle-to-level timer), and a WAAPI landing tween from the drag overlay to a drop-hole placeholder's real rect on release (`cubic-bezier(.25,.7,.2,1)`, duration scaled to landing distance).
- Confirmed two scoping decisions with the user before designing: (1) the "grid" is a two-column stack (left/right columns fixed in position/width, the center block never becomes a grid item and never moves — it's a plain flex sibling `WidgetGrid` passes through as `children`, untouched), not a free-form dashboard-grid engine; (2) layout (column/order/height) is cloud-synced, a third optional `panelLayout` field on the same `workspace` JSON blob, following the exact `todos`/`timesheet` no-schema-change pattern from earlier the same day.
- **Deliberately did not extract a shared drag hook from `SortBoard.tsx`.** Wrote a new, self-contained implementation in `src/components/widgets/WidgetGrid.tsx` that mirrors the same constants and technique (same `LAND_EASE`, same velocity-EMA formula, same snapshot-at-pickup approach) instead. Reasoning: refactoring already-shipped, only-manually-tested code to share ~150 lines with a new feature is a real but small win, versus a real regression risk to a working component — not worth it right now. Worth doing later if a third drag surface appears.
- **One deliberate deviation from SortBoard's literal technique:** SortBoard's dragged item (`LinkCard`) is presentation-only, so its overlay is a live clone of the actual card. The To-Do/Timesheet widgets are stateful and interactive (checkboxes, a running clock with a `setInterval`), so cloning their real rendered content into a second on-screen copy during drag would have created duplicate interactive DOM (two checkboxes wired to the same handler, two ticking timers) — a real correctness bug, not just a cosmetic one. The drag overlay is instead a lightweight non-interactive preview chip (icon + widget title only); the real widget is fully removed from its column's rendering for the duration of the drag (same as how SortBoard's dragged card disappears from its source list) and reappears, fully live, in its new position once the layout commit happens on drop.
- **Not yet done, at the time it was written:** the actual drag/resize/snap interaction had not been exercised in a browser — the Claude-in-Chrome extension was not connected that session, so verification stopped at `npm run lint`, both Vite builds, PHP lint, and `package.ps1 -NoBump` packaging. This was a materially bigger gap than the to-do/timesheet panels' own "not yet live-checked" status above, since interaction code (pointer math, hit-testing, WAAPI timing) is exactly the category of bug that type-checking and a successful build cannot catch. Confirmed exactly right: the user then tested it by hand and found two real bugs neither `tsc` nor a successful build could have caught —
  - **Resize grew the transparent wrapper, not the visible card.** `WidgetShell.tsx` set a fixed `height` on the wrapper `div` it renders around a widget's own content (`TodoPanel`/`TimesheetPanel`'s root `glass-card` div), but that inner `glass-card` still sized itself to its own content (its default, auto-height behavior) — so resizing taller just grew empty wrapper space below the card, which looked like a blank/transparent gap. Fixed by adding `min-h-full` to the wrapper's direct child (Tailwind arbitrary child-selector `[&>:first-child]:min-h-full`) so the card stretches to fill the wrapper, plus an equivalent imperative `element.style.minHeight = '100%'` write in `WidgetGrid.tsx`'s live-resize handler so the *live drag preview* (before React re-renders with the committed height) shows the same fix, not just the state after release.
  - **A permanent scrollbar appeared even when content didn't need to scroll.** The resize handle is deliberately positioned a few px *outside* the wrapper's bottom edge (`-bottom-1.5`) so it reads as a handle on the card's border rather than floating inside the content. But `overflow-y: auto` was on that same wrapper element — and a `position: absolute` descendant that extends past its containing block's edge counts toward that element's *scrollable overflow area*, even though nothing about the actual widget content overflowed. The wrapper was permanently "1 handle's-worth" taller than its own box, so it always scrolled. Fixed by splitting the wrapper in two: an *outer* element (owns the fixed height, `position: relative`, default `overflow: visible`) that hosts the grip/resize-handle chrome, and a separate *inner* element (owns `overflow-y: auto`) that wraps only `{children}` — so the handle's intentional overhang no longer contributes to the scrollable box it's inside.
  - **Lesson for next time a resize/scroll interaction is built in this app:** a wrapper that both (a) forces a child to a fixed height via CSS and (b) hosts absolutely-positioned decorative chrome that intentionally overflows its own edge should almost never also be the element with `overflow: auto` — split "the box that scrolls" from "the box that positions overflowing decoration" into two nested elements, or the decoration itself silently becomes "content" as far as the scrollbar is concerned.

### 2026-08-03

- Fixed eight Elementor/theme-isolation rendering gaps described in Status above (plugin 0.4.21-0.4.27), all latent since the isolation-CSS technique was ported from the sibling Little Steps project (2026-07-31 decision below) — that project's own page apparently never hit these, or was never checked closely enough, so they went unnoticed until now. Rather than keep these as tribal knowledge specific to this repo, wrote up the general technique and every gotcha hit as a standalone, project-agnostic guide: [`block-elementor.md`](./block-elementor.md). Established patterns for the future:
  - Any global reset (`all: initial`) applied to the shortcode's mount point only resets that one element, not its descendants — every inherited value the app actually still depends on further down (fonts, ligature-font-based icons, native `<button>`/`<a>` chrome) needs its own explicit re-declaration, not just assumed to survive. And that re-declaration must reference the *actual* variable the app's own runtime theming sets — an early attempt referenced a variable (`--font-sans`) nothing ever set, so it silently always fell back to a static default, which looked fine at a glance but quietly broke font-pair switching for everything except headings (which have their own separate, correct rule) until caught and fixed in 0.4.26.
  - `contain: layout` (needed to isolate the app's layout from Elementor's) makes its element the containing block for `position: fixed` descendants instead of the true viewport. This is a broader trap than it first appears: it doesn't just affect elements meant to pin to the true screen edge (the Cat companion's overlay), it affects *every* `fixed`-positioned element, including ones that specifically want to center on the actual visible screen (modals) — and once removed to fix those, elements that specifically want to anchor *below the host page's own chrome* (the top nav bar, which needs to sit under WordPress's admin toolbar rather than at the literal viewport top) broke in the opposite direction and needed their own explicit fix. The real lesson: don't reach for `contain: layout` as a default "isolate everything" hammer — decide, per `position: fixed` element, whether it wants the true viewport or the host chrome-aware frame, and solve that explicitly (a `--host-chrome-offset` custom property, consumed only where the "anchor below host chrome" behavior is actually wanted) rather than relying on containment to accidentally get one of them right.
  - Tailwind v4 (and any `@layer`-based tool) generates utilities inside a named CSS layer, which reverses `!important` priority: any layered `!important` rule beats any unlayered one regardless of specificity. An override with no `@layer` of its own can silently lose to a Tailwind utility no matter how specific its selector looks — this cost a full extra deploy-and-verify cycle (0.4.24) before being correctly diagnosed and fixed in 0.4.25, which was itself later replaced entirely once the same underlying `contain: layout` issue was traced to a simpler root fix in 0.4.26 (see above) — the layer trick was real and worked, but wasn't actually the best fix once the full picture was understood.
  - Don't trust any WordPress/Elementor CSS fix as verified from local dev — build a tiny standalone static-HTML repro of the exact CSS mechanism (with a script reading back `getComputedStyle`/`getBoundingClientRect`) to confirm the theory *before* spending a deploy cycle on it, then confirm again live afterward. This caught a wrong turn before it reached production more than once in this round.
  - After any isolation.css change, re-check the *whole* hosted page, not just the one symptom that was reported — several of these fixes surfaced a new, previously-hidden bug precisely because the old (buggy) behavior had been accidentally compensating for something else.

## Lessons learned

- Verify the actual network verb, endpoint, response status, and persisted server version before diagnosing client refresh behavior.
- A generic sync warning hid several distinct failures; retain status/code diagnostics.
- Shared hosts may strip `Authorization`; use the scoped `X-LinkFlow-Token` header and verify CORS preflight live.
- `wp_http_validate_url()` is for outbound server requests and is too restrictive for stored bookmarks.
- Tauri production artifacts must be built with `tauri build`; a direct Cargo executable can point at the development URL.
- On this workstation, force the MSVC target and toolchain paths to avoid inheriting the GNU Rust toolchain.
- Keep plugin and desktop versions separate, but document their compatible pairing in every release.
- A startup GET is not downward synchronization for an already-open client; document the actual refresh frequency precisely.
- Correlated evidence must cover success as well as failure. A green HTTP status without the user ID, returned version, and affected-row result is not enough.
- Verbose support logs must redact credentials at the logging boundary, before persistence or display.
- The install ZIP filename includes the release version, but no version may appear in its internal plugin root. The release contract is `linkflow-dashboard-vX.Y.Z.zip` containing `linkflow-dashboard/`.
- Validate ZIP entry paths programmatically; visual inspection of the source directory is not proof of the extracted WordPress folder name.
- WordPress packages built on Windows must use forward slashes in ZIP entry names; otherwise a Linux host can fail to extract `linkflow-dashboard/linkflow-dashboard.php` as a real plugin file.
- Do not use the plugin package version as the database migration marker: package-only releases would force unnecessary `dbDelta()` work and can make activation/upgrades appear to stall on a shared host.
- A cross-platform credential crate (`keyring`) can compile and run with zero errors while silently using an in-memory, non-persistent mock backend; it requires an explicit platform feature (`windows-native`) to reach the real OS credential store. Verify with an actual two-process persistence test, not just that the save/load calls succeed.
- This workstation's default Rust toolchain can silently be GNU even with an MSVC toolchain also installed (`rustup show`); an unqualified `cargo`/`tauri` command then builds against the wrong one. Set the default explicitly rather than relying on the `--target` flag alone.
- A validated packaging script (backslash/root/main-file checks) only prevents *future* bad installs; it cannot repair one already deployed. When a live activation fails, inspect the actual files on the server before assuming the packager regressed.
- `wp_add_inline_script()` is not reliable for a script registered with `type="module"` on all WordPress core versions in use in production — the module `<script>` tag can print while its attached inline content is silently dropped, with no error anywhere. Prefer printing required runtime config (like `window.linkflowConfig`) as a plain classic inline `<script>` in the shortcode's own HTML output.
- A page rendering without visible errors is not proof its cloud configuration succeeded — check the diagnostics panel's `cloudBackendPresentAtMount` value specifically, since a page can mount and run entirely on local cache while never talking to the server.
- When adding any third-party content feed (quotes, verses, etc.), fetch it server-side and cache it, never call it directly from the client: avoids CORS gaps on the provider's free tier, keeps API keys off the client bundle, and gives one place to add a fallback source.
- A UI element that renders nothing when its data is unavailable also removes any way to reach its own settings/toggle control if that control only exists inside the "has data" render branch. Always keep a stable, always-rendered affordance (even a small "unavailable" state) rather than conditionally rendering the entire component away.
- A file-download pattern that works in every real browser (`<a download href="data:...">`) can silently fail inside Tauri's WebView2 shell with no console error at all. Any desktop save-to-disk feature needs a native path (dialog plugin + a Rust-side write, or the fs plugin with proper scope) rather than reusing the browser's download trick.
- `contain: layout`/`paint`/`strict`/`content` makes its element the containing block for `position: fixed` (not just `absolute`) descendants — this affects *every* fixed element inside it, not just the one you're currently debugging: it broke both a full-viewport overlay meant to pin to the true screen edge (the cat) and, in the opposite direction, every centered modal overlay (which needed the true viewport, not the containing element's full scrollable height). The eventual fix here was to stop using `contain: layout` at all (`contain: style` alone was enough for what this project actually needed from containment) rather than patch around its side effects piecemeal. See `block-elementor.md`.
- Once `position: fixed` correctly tracks the true viewport again, remember that not every fixed element *wants* that: a top nav bar meant to sit below a host page's own chrome (WordPress's admin toolbar) needs to know about that chrome explicitly (a `--host-chrome-offset`-style custom property), whereas a centered modal or a viewport-anchored overlay wants the true, unadjusted viewport. Don't assume all `position: fixed` elements in an app want the same reference frame.
- The WordPress admin bar shifts the whole page down via `margin-top` on `<html>` without changing `window.innerHeight`; any `100vh`-based sizing inside the page (including Tailwind's `min-h-screen` utility on nested wrappers, not just an outer container) silently overflows the true viewport bottom by that same amount *if* something (like `contain: layout`) has made a `position: fixed` element's containing block track that box instead of the true viewport. Once containment is out of the picture, this stops mattering for `fixed` elements — but still matters for anything computing its own layout height directly from `100vh`.
- Tailwind v4's generated utilities live inside `@layer utilities { ... !important }`. Per the CSS cascade-layers spec, `!important` priority is the reverse of normal priority: a layered rule beats an unlayered rule regardless of specificity. An override stylesheet needs its own (even unnamed-relative-to-Tailwind) `@layer`, declared before Tailwind's own layers first appear on the page, to have any chance of winning an `!important` fight against a Tailwind utility — a plain higher-specificity `!important` rule is not enough and can fail in a way that looks like a mistake in the selector when it isn't. (Still true and still useful in general — just turned out not to be the fix actually needed here once the deeper `contain: layout` cause was found.)
- A CSS variable used as a fallback (`var(--x, ...)`) is silent when `--x` is never actually set by anything — it just always uses the fallback, with no error, no warning, nothing visibly wrong until you specifically test the feature that variable was supposed to drive. Double-check that any variable referenced in a "safety net" CSS rule is the same one the app's own runtime code actually sets, not a plausible-looking name that happens to not exist.
- After fixing one reported CSS bug in an isolation wrapper, re-check the rest of the page before calling it done — several fixes in this round each surfaced the next bug, because the previous (buggy) behavior had been accidentally compensating for something else.
- All of the above (plus the font/icon-loading and native-control-reset lessons from earlier in this session) are written up generally, for reuse outside this repo, in `block-elementor.md`.
- A bare `data-tauri-drag-region` (no value, or `"true"`) only starts a Tauri window drag when the raw click **target** (`event.composedPath()[0]`) is that exact element — not any descendant. If the element wraps any child content (an icon, text, anything at all), the click's real target is the child, the bare form's check silently never matches, and dragging does nothing with no error anywhere. Use `data-tauri-drag-region="deep"` for any drag region that isn't a true leaf DOM node.
- A missing Tauri window-permission (e.g. `core:window:allow-start-dragging`) can fail completely silently in a production build — no console error, no visibly denied-permission log — leaving a feature that looks fully implemented in source just not work at all. When a Tauri window API call does nothing with no error, check the window's capability file for the specific permission before assuming the JS/React logic is wrong.
- Windows' tray icon defaults to opening the context menu on a plain left-click as well as a right-click; if the tray also needs a distinct left-click action (e.g. toggle), call `.show_menu_on_left_click(false)` on the `TrayIconBuilder` or the two handlers will fight each other.
- A dynamic tray/window icon (state-dependent color or glyph) doesn't need an image asset at all — drawing it as raw RGBA pixels in Rust (`tauri::image::Image::new_owned`) is simpler than shipping and swapping between multiple PNGs, and trivially supports any number of states.
